1. Project Overview

Task Tracker is a standalone desktop to-do list application implemented in Java 11 with Swing and SQLite
accessed through JDBC. Different registered users can log in to the same local application, create tasks,
assign tasks to other registered users and track completion. This simulates collaboration through sequential
sessions on one computer; it does not provide real-time networking or cloud synchronization.
The assignment explicitly requires requirements analysis, design, implementation, unit testing, documenta-
tion and a presentation. The project also includes priority levels, optional deadlines and filtering/sorting as
additional features.

3. Use Cases and Authorization

Visitor: register or log in. Signed-in user: create tasks, assign tasks and view/filter relevant tasks. Creator:
edit, delete and toggle completion. Assignee: view and toggle completion. Unrelated user: cannot view
or mutate another user’s task.

4. System Architecture

The implementation is MVC-oriented with clear separation of responsibilities. MainFrame is the Swing
view; TaskTrackerController manages the logged-in session and coordinates actions; AuthService
and TaskService implement business rules; repositories encapsulate SQL; and Database creates connec-
tions and initializes the schema. Data objects are User and TaskItem.

5. Database Design

The application creates one local tasks.db file. The users table contains a case-insensitive unique user-
name and the password hash. The tasks table includes separate foreign keys to the creator and assignee.
Indexes support filtering by creator, assignee and due date.




               Figure 3: SQLite entity relationship diagram (two foreign keys into users).


Integrity: SQLite enforces a primary key, foreign keys, an enumeration constraint for priority and a
Boolean-like completion constraint. Each JDBC connection executes PRAGMA foreign_keys=ON. SQL
statements use bound parameters rather than assembling user-provided strings into SQL.


6. Implementation Decisions

• Local-first application: no database server or external runtime services are needed.


                                                    4
• Password handling: random per-user salts and PBKDF2-HMAC-SHA256 hashes; plaintext passwords
  are not stored in the database.
• Authorization: the service layer checks roles and SQL updates/deletions include the relevant user ID in
  their WHERE conditions.
• Validation: names, passwords, title lengths, priority values, dates and target users are checked before
  task writes.
• User experience: the same local database is used by different accounts; assignment, priority and filtering
  remain simple enough for a four-week coursework project.


7. Testing and Evidence

JUnit 5 integration and password tests are present in source code. They cover registration, credential
verification, authorization, assignment, task lifecycle, validation, data persistence, SQLite constraints and
injection-like strings. Four additional JUnit cases were added for direct repository authorization, self/other
assignment, validation and reassignment.
Executed evidence: mvn -B clean verify passed all 17 JUnit 5 tests (0 failures, errors or skips) with
SQLite JDBC; the packaged JAR completed a SQLite round trip; and 10 independent Python SQLite checks
passed. The seven PlantUML diagrams were rendered to PNG and SVG. Manual end-to-end GUI accep-
tance, GitHub Actions and real team contributions remain unverified. The companion Test Report docu-
ments the evidence and exact acceptance scenarios.
